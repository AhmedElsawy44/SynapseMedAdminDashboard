SYNAPSE MED — ADMIN UI
PROMPT #08 — REVISIONS LIST

Design the Revisions List page for the SYNAPSE MED Admin Console.

The approved SYNAPSE MED Admin App Shell is immutable.

Reuse the existing SYNAPSE MED Design System.

==================================================
1. PRODUCT PURPOSE
==================================================

The Revisions page manages Course Revision records.

A Revision represents a version/state of educational content associated
with a Course.

This page is lifecycle-driven.

The administrator needs to understand:

- which revisions exist
- which Course they belong to
- their lifecycle state
- their availability window
- what action is currently possible

==================================================
2. REVISION LIFECYCLE
==================================================

The Revision lifecycle is:

Draft
↓
Scheduled
↓
Active
↓
Inactive
↓
Archived

These are the approved Revision states.

DO NOT invent additional lifecycle states.

Do not use Course statuses here.

==================================================
3. PAGE HEADER
==================================================

Breadcrumb:

Admin / Revisions

Title:

Revisions

Description:

Use concise operational copy.

If revision creation is supported:

Primary action:

Create Revision

Do not add unsupported actions.

==================================================
4. SEARCH
==================================================

Search should allow administrators to locate revisions using
supported revision information.

The platform search model supports Revision title.

Use:

Search revisions...

Do not invent additional searchable fields.

==================================================
5. FILTERS
==================================================

Create filters based on the Revision lifecycle.

Primary filter:

Status

Values:

Draft

Scheduled

Active

Inactive

Archived

Additional filters may only be added if supported by the product model.

Do not invent:

Instructor

Department

Revenue

Performance

Rating

==================================================
6. LIFECYCLE VISUALIZATION
==================================================

Status must be visually clear.

Use the existing status badge system.

Each status should have a restrained semantic treatment.

Do not use five completely unrelated bright colors.

The visual language should remain calm.

==================================================
7. AVAILABILITY
==================================================

Revision availability is represented by:

available_from

available_until

Show these dates when supported.

Use a readable date/time format.

The UI should make the availability window understandable.

Do not expose database field names.

==================================================
8. REVISION TABLE
==================================================

Use the approved DataTable system.

Conceptual columns:

Revision

Course

Status

Available From

Available Until

Actions

Only show fields supported by the actual data model.

Do not invent additional metrics.

==================================================
9. REVISION IDENTITY
==================================================

Show:

Revision title/name

Optional approved secondary information

The Revision should remain visually connected to its parent Course.

==================================================
10. COURSE RELATIONSHIP
==================================================

Every Revision is associated with a Course.

The UI should make this relationship clear.

Use:

Course name

as secondary information.

Do not duplicate the entire Course object.

==================================================
11. DATE DISPLAY
==================================================

Dates should be readable.

If a revision is:

Draft:

Availability may be absent.

Scheduled:

Future availability should be clearly visible.

Active:

Current availability should be clear.

Inactive:

The previous availability window may remain visible if supported.

Archived:

Use subdued presentation.

Do not create custom lifecycle logic beyond the defined model.

==================================================
12. ROW ACTIONS
==================================================

Actions must respect lifecycle.

Only show actions explicitly supported.

Potential actions may include:

View

Edit

Activate

Schedule

Archive

BUT:

These actions must only appear if supported by the actual workflow.

Do not assume every status allows every action.

Do not invent transition buttons.

==================================================
13. LIFECYCLE ACTION UX
==================================================

If a lifecycle transition is available:

The action should clearly communicate the transition.

Example:

Schedule Revision

Activate Revision

Archive Revision

Use confirmation when the transition is consequential.

Do not use generic:

"Change Status"

when a specific action is clearer.

==================================================
14. STATUS TRANSITION SAFETY
==================================================

Never allow the UI to imply an invalid lifecycle transition.

The UI should follow:

Draft
→ Scheduled
→ Active
→ Inactive
→ Archived

Do not visually expose impossible transitions.

Do not allow Archived to appear editable like Draft.

==================================================

This page should feel like:

A controlled content lifecycle management interface.

WHAT STATE it is in

WHEN it becomes available
